# Testing Strategy MVP LifePilot

## Назначение документа

Этот документ описывает ручную стратегию тестирования LifePilot MVP перед каждым commit, push и pull request. Он нужен, чтобы проверять основной пользовательский сценарий, локальное хранение, risk level, категории и mobile-first интерфейс без добавления новых инструментов или зависимостей.

## Общий подход

Текущий MVP тестируется вручную в браузере. Главная цель проверки — убедиться, что пользователь может пройти линейный сценарий:

1. открыть главный экран;
2. создать новый кейс;
3. вставить текст;
4. запустить анализ;
5. увидеть состояние анализа;
6. открыть результат;
7. проверить локально определенную категорию, risk level и рекомендации;
8. открыть немецкий черновик;
9. вернуться к истории;
10. открыть сохраненный кейс из истории.

Перед push важно проверять не только happy path, но и пустые состояния, ошибки ввода, поведение `localStorage`, безопасность Supabase foundation layer и мобильную читаемость.

## Тестовые данные

Для ручной проверки достаточно трех коротких текстов.

Low risk:

```text
Guten Tag, wir bestätigen den Eingang Ihrer Nachricht und melden uns in den nächsten Tagen.
```

Medium risk:

```text
Bitte senden Sie die angeforderten Unterlagen bis zum 15. Juni. Der Betrag beträgt 120 Euro.
```

High risk:

```text
Mahnung wegen Schulden. Bei Nichtzahlung drohen Inkasso, Kündigung oder gerichtliche Schritte.
```

Категории для проверки:

- `Жильё`;
- `Страховка`;
- `Работа`;
- `Документы`;
- `Другое`.

## Home Screen

- [ ] Главный экран открывается без ошибки.
- [ ] Видно основное действие для создания нового кейса.
- [ ] Переход `Новый кейс` открывает экран создания кейса.
- [ ] Переход в `История` открывает список локальных кейсов или empty state.
- [ ] Переход в `Безопасность` открывает экран правил и ограничений.
- [ ] Экран не выглядит как чат без границ ответственности.
- [ ] На мобильной ширине основные действия не перекрывают друг друга.

## New Case Flow

- [ ] Экран `Новый кейс` открывается без ошибки.
- [ ] Поле textarea принимает короткий текст.
- [ ] Поле textarea принимает длинный текст без поломки layout.
- [ ] Категория определяется локально после запуска анализа.
- [ ] UI не обещает ручной выбор категории на текущем этапе.
- [ ] Пустой текст не создает кейс.
- [ ] При пустом тексте показывается понятное inline-предупреждение.
- [ ] После исправления текста warning исчезает или не мешает отправке.
- [ ] После нажатия `Анализировать` создается текущий кейс.
- [ ] После запуска анализа пользователь попадает на экран `Анализ`.

## Analysis State

- [ ] Экран `Анализ` открывается после создания кейса.
- [ ] Видно понятное loading-состояние.
- [ ] Видны шаги обработки: чтение текста, оценка риска, подготовка результата.
- [ ] Если текущего кейса нет, экран не остается пустым и возвращает пользователя к созданию кейса.
- [ ] После короткого ожидания пользователь попадает на экран `Результат`.
- [ ] Loading state не обещает юридическую проверку или гарантированную точность.

## Result Screen

- [ ] Экран `Результат` читает текущий кейс из `localStorage`.
- [ ] Показывается краткий анализ исходного текста.
- [ ] Показывается локально определенная категория.
- [ ] Показывается risk badge.
- [ ] Показывается короткое объяснение риска.
- [ ] Показываются рекомендации по следующему шагу.
- [ ] Кнопка перехода к черновику работает.
- [ ] Если текущего кейса нет, показывается безопасное empty state и действие `Новый кейс`.
- [ ] Результат не выглядит как юридическая гарантия.

## Draft Screen

- [ ] Экран `Черновик` открывается из результата.
- [ ] Немецкий текст читается как письмо, а не как маленькое поле.
- [ ] Видно предупреждение, что это черновик, а не юридическая консультация.
- [ ] Плейсхолдер `[Ihr Name]` заметен.
- [ ] Текст можно прочитать на мобильной ширине без горизонтального скролла.
- [ ] Экран не создает впечатление автоматической отправки письма.

## History Flow

- [ ] Новый непустой кейс появляется в истории.
- [ ] История хранится после перезагрузки страницы.
- [ ] Карточка истории показывает preview текста.
- [ ] Карточка истории показывает категорию.
- [ ] Карточка истории показывает risk badge.
- [ ] Карточка истории показывает дату.
- [ ] Открытие кейса из истории восстанавливает его как текущий кейс.
- [ ] После открытия из истории пользователь видит экран результата выбранного кейса.
- [ ] Очистка истории удаляет список прошлых кейсов в браузере.
- [ ] Empty state истории предлагает создать новый кейс.

## Risk Level

- [ ] Low risk текст получает уровень `low` или визуальную метку `Низкий`.
- [ ] Medium risk текст получает уровень `medium` или визуальную метку `Средний`.
- [ ] High risk текст получает уровень `high` или визуальную метку `Высокий`.
- [ ] High risk результат содержит осторожные рекомендации.
- [ ] Risk badge всегда сопровождается текстом, а не только цветом.
- [ ] Risk level не подается как юридическая оценка.
- [ ] Если старый кейс в истории не содержит `riskLevel`, результат не ломается.

## Категории кейсов

- [ ] Категория определяется локально через анализ текста, а не ручным selector.
- [ ] `Жильё` может сохраняться и отображаться в результате для подходящего текста.
- [ ] `Страховка` может сохраняться и отображаться в результате для подходящего текста.
- [ ] `Работа` может сохраняться и отображаться в результате для подходящего текста.
- [ ] `Документы` могут сохраняться и отображаться в результате для подходящего текста.
- [ ] `Другое` используется как fallback для нераспознанной категории.
- [ ] Категория отображается в карточке истории.
- [ ] Для старых локальных кейсов без категории используется резервное значение `Другое`.

## LocalStorage Behavior

- [ ] После создания кейса появляется `lifepilot.currentCase`.
- [ ] После создания кейса обновляется `lifepilot.caseHistory`.
- [ ] `lifepilot.currentCase` содержит исходный текст, категорию, статус, дату обновления и risk level.
- [ ] `lifepilot.caseHistory` хранит массив кейсов.
- [ ] Перезагрузка страницы не удаляет историю.
- [ ] Очистка истории удаляет `lifepilot.caseHistory`.
- [ ] Действие `Открыть результат` из истории заново записывает выбранный кейс в `lifepilot.currentCase`.
- [ ] Detail route `/history/[caseId]` показывает кейс из истории и не требует изменения `lifepilot.currentCase`.
- [ ] Поврежденная или пустая история не ломает экран истории.
- [ ] Данные не передаются через URL.

## Supabase Foundation Layer

- [ ] `.env.example` существует и содержит только публичные Supabase-переменные без реальных ключей.
- [ ] `.env.local` не отслеживается Git и не попадает в commit.
- [ ] UI создания, результата, истории и детального просмотра продолжает работать через `localStorage`.
- [ ] Supabase не подключен к пользовательскому flow и не заменяет локальную историю.
- [ ] `readSupabaseCases()` существует только как подготовительная функция и не является источником данных UI.
- [ ] Supabase client создается в одном месте и не дублируется.
- [ ] В клиентском коде не используются `service_role` ключи или приватные токены.
- [ ] Таблица `public.cases` описана в specs и соответствует TypeScript-типам.
- [ ] RLS для `public.cases` включен, SELECT policy для anon role отсутствует, и это не ломает `localStorage` flow.
- [ ] Ошибка или отсутствие Supabase-конфигурации не ломает локальный MVP.

## Auth/Admin Foundation Readiness

Этот раздел проверяет только готовность документации к будущей реализации Auth/Admin. Код, UI, migrations, env и Supabase schema не должны меняться без отдельного approval.

- [ ] [../architecture/auth-admin-foundation-decision-review.md](../architecture/auth-admin-foundation-decision-review.md) является source of truth для Auth/Admin решений.
- [ ] [../specs/auth-spec.md](../specs/auth-spec.md) описывает login, logout, session validation, protected routes, auth states и error states.
- [ ] [../specs/admin-spec.md](../specs/admin-spec.md) описывает admin identity, allowlist flow, admin access rules и admin session rules.
- [ ] [../specs/database-auth-model.md](../specs/database-auth-model.md) описывает `auth.users`, `public.admin_users`, связи, поля и ограничения.
- [ ] [../specs/security-model.md](../specs/security-model.md) описывает server-side only operations, service role boundaries, env variables и forbidden client operations.
- [ ] [../architecture/routing-map.md](../architecture/routing-map.md) содержит будущие routes `/admin/login` и `/admin`.
- [ ] [../architecture/state-management.md](../architecture/state-management.md) фиксирует, что auth state не хранится в `localStorage` LifePilot MVP.
- [ ] [../plans/admin-users-migration-plan.md](../plans/admin-users-migration-plan.md) описывает migration plan для `public.admin_users`.
- [ ] План Auth/Admin и Vercel не используется как source of truth вместо ADR и specs.
- [ ] Реализация Auth/Admin начинается только после отдельного approval.

## Auth/Admin Future Implementation Checks

Эти проверки выполняются только после approval и реализации Auth/Admin.

- [ ] `/admin/login` доступен как public route.
- [ ] `/admin/login` использует Supabase Auth email/password.
- [ ] Magic link и signup через UI не реализованы.
- [ ] Успешный login ведет на `/admin`.
- [ ] `/admin` проверяет session server-side до показа admin content.
- [ ] `/admin` проверяет active запись в `public.admin_users`.
- [ ] Пользователь без session получает redirect на `/admin/login`.
- [ ] Пользователь без active admin record не получает admin content.
- [ ] Logout закрывает admin session и не очищает `lifepilot.caseHistory`.
- [ ] Auth session, password, access token, refresh token, role и allowlist data не сохраняются в `localStorage`.
- [ ] Client-side UI не читает `public.admin_users` напрямую через browser anon client.
- [ ] Service role key не используется во frontend.
- [ ] Admin page не читает и не изменяет `public.cases` без отдельного RLS/data-access review.
- [ ] Основной пользовательский MVP остается public и local-first.

## Mobile-First Visual Checks

- [ ] Проверена ширина около 360 px.
- [ ] Проверена ширина около 390 px.
- [ ] Проверена ширина около 430 px.
- [ ] Нет горизонтального скролла.
- [ ] CTA не перекрывает контент.
- [ ] Header не занимает слишком много места.
- [ ] Карточки не вложены друг в друга.
- [ ] Preview текста в истории не ломает карточку.
- [ ] Risk и category badges помещаются на мобильной ширине.
- [ ] Textarea удобно использовать с открытой клавиатурой.
- [ ] Длинный немецкий черновик читается без визуальной тесноты.

## Error и Empty States

- [ ] Пустой ввод показывает inline-warning.
- [ ] Результат без текущего кейса показывает empty state.
- [ ] История без записей показывает empty state.
- [ ] Неизвестный маршрут показывает fallback или not found.
- [ ] Ошибка не обвиняет пользователя.
- [ ] Empty state всегда дает безопасное следующее действие.
- [ ] Введенный текст не очищается без явного действия пользователя.

## Regression Checklist перед push

- [ ] Проверен полный happy path: Home -> New Case -> Analysis -> Result -> Draft.
- [ ] Проверен flow истории: создать кейс -> открыть историю -> открыть результат.
- [ ] Проверены low, medium и high risk тексты.
- [ ] Проверено локальное определение категорий на разных текстах.
- [ ] Проверен пустой ввод.
- [ ] Проверено отсутствие текущего кейса на `/case/result`.
- [ ] Проверено отсутствие текущего кейса на `/case/analyzing`.
- [ ] Проверена история после перезагрузки страницы.
- [ ] Проверена очистка истории.
- [ ] Проверен mobile layout.
- [ ] `npm run build` проходит без ошибок.
- [ ] Проверено, что нет backend, auth, OCR, PDF parser, billing или sync в MVP.
- [ ] Проверено, что Supabase foundation остается schema/client слоем без разрешенного anon SELECT и не подключен к пользовательскому UI-flow.
- [ ] Проверено, что Auth/Admin implementation не начиналась без отдельного approval.
- [ ] Проверено, что warnings и ограничения не исчезли из UI.
- [ ] Проверено, что измененные документы не противоречат `docs/plans/mvp-scope.md`.

## Когда checklist считается пройденным

Checklist считается пройденным, если основной сценарий работает без блокирующих ошибок, локальная история восстанавливается после перезагрузки, risk level отображается ожидаемо, а мобильный интерфейс остается читаемым и спокойным.

Если найдено поведение, которое противоречит scope MVP, сначала обновляется документация в `docs/specs` или `docs/plans`, затем меняется реализация.
