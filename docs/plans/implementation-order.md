# Порядок реализации LifePilot

## Назначение документа

Этот документ фиксирует точный порядок реализации MVP LifePilot. Этапы нужно проходить последовательно: каждый следующий этап опирается на готовность предыдущего.

Главный принцип: сначала структура и навигация, потом визуальный скелет, затем основная логика, потом история и только после этого polish.

## Этап 1 — Scaffold

Что делается:
- Next.js app router
- layouts
- маршруты
- пустые страницы
- mobile container
- navigation

Что нельзя делать:
- AI-логику
- storage
- history
- backend
- auth

Зависимости:
- этап не зависит от бизнес-логики;
- маршруты должны соответствовать MVP-сценарию;
- структура должна быть готова для следующих UI-экранов.

Критерий готовности:
- можно открыть все страницы;
- навигация работает;
- нет бизнес-логики.

---

## Этап 2 — UI skeleton

Что делается:
- textarea
- buttons
- блоки предупреждений
- пустые состояния
- состояния загрузки
- mobile spacing

Что нельзя делать:
- генерацию ответа;
- local storage;
- сохранение истории.

Зависимости:
- этап начинается только после готового scaffold;
- все элементы должны быть привязаны к экранному сценарию;
- состояния должны быть визуальными, без реальной бизнес-логики.

Критерий готовности:
- весь сценарий визуально существует.

---

## Этап 3 — Основная логика

Что делается:
- анализ текста
- определение категории
- определение риска
- структура ответа
- pipeline генерации

Что нельзя делать:
- backend;
- синхронизацию;
- OCR;
- PDF parser.

Зависимости:
- этап начинается после визуального скелета;
- основная логика должна использовать уже определенные экраны и состояния;
- правила риска должны соответствовать safety-документам.

Критерий готовности:
- пользователь может пройти полный MVP-сценарий.

---

## Этап 4 — History

Что делается:
- localStorage
- список кейсов
- удаление кейса
- открытие кейса

Что нельзя делать раньше времени:
- добавлять синхронизацию между устройствами;
- добавлять аккаунты;
- добавлять database;
- добавлять серверный поиск, синхронизацию фильтров или расширенные фильтры за пределами локального MVP-flow.

Зависимости:
- этап начинается после рабочего основного сценария;
- структура кейса должна быть стабильной;
- сохранение не должно ломать безопасные состояния и warning.

Критерий готовности:
- история переживает перезагрузку страницы.

---

## Этап 5 — Polish

Что делается:
- accessibility
- mobile UX
- крайние состояния
- тексты предупреждений
- validation
- оптимизацию загрузки

Что нельзя делать раньше времени:
- расширять scope MVP;
- добавлять OCR;
- добавлять PDF parser;
- добавлять backend;
- добавлять auth;
- добавлять синхронизацию;
- добавлять будущие функции вместо стабилизации MVP.

Зависимости:
- этап начинается после scaffold, UI skeleton, основной логики и истории;
- все основные пользовательские состояния должны уже существовать;
- polish должен улучшать MVP, а не менять его границы.

Критерий готовности:
- MVP стабилен и готов к demo.

## Общие запреты до готовности этапов

- Не начинать AI-логику до готового scaffold и UI skeleton.
- Не начинать историю до прохождения полного MVP-сценария.
- Не добавлять backend, auth, OCR, PDF parser или синхронизацию в рамках MVP.
- Не добавлять Stripe, billing, payment flow, подписки или тарифные лимиты в рамках MVP.
- Не расширять маршруты под будущие функции до завершения основного сценария.
- Не добавлять сложную архитектуру, если текущий этап не требует ее для готовности.

## Итоговая последовательность

1. Scaffold.
2. UI skeleton.
3. Основная логика.
4. История.
5. Polish.

Нарушение порядка допустимо только если сначала обновлены планы и явно объяснена причина изменения.
