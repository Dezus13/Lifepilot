# Implementation Order LifePilot

## Назначение документа

Этот документ фиксирует точный порядок реализации MVP LifePilot. Этапы нужно проходить последовательно: каждый следующий этап опирается на готовность предыдущего.

Главный принцип: сначала структура и навигация, потом визуальный скелет, затем core logic, потом история и только после этого polish.

## Этап 1 — Scaffold

Что делается:
- Next.js app router
- layouts
- routes
- пустые страницы
- mobile container
- navigation

Что нельзя делать:
- AI logic
- storage
- history
- backend
- auth

Зависимости:
- этап не зависит от бизнес-логики;
- маршруты должны соответствовать MVP flow;
- структура должна быть готова для следующих UI-экранов.

Критерий готовности:
- можно открыть все страницы;
- navigation работает;
- нет business logic.

---

## Этап 2 — UI skeleton

Что делается:
- textarea
- buttons
- warning blocks
- empty states
- loading states
- mobile spacing

Что нельзя делать:
- генерацию ответа;
- local storage;
- сохранение истории.

Зависимости:
- этап начинается только после готового scaffold;
- все элементы должны быть привязаны к экранному flow;
- состояния должны быть визуальными, без реальной бизнес-логики.

Критерий готовности:
- весь flow визуально существует.

---

## Этап 3 — Core logic

Что делается:
- анализ текста
- category detection
- risk detection
- response structure
- generation pipeline

Что нельзя делать:
- backend;
- sync;
- OCR;
- PDF parser.

Зависимости:
- этап начинается после визуального skeleton;
- core logic должна использовать уже определенные экраны и состояния;
- правила риска должны соответствовать safety-документам.

Критерий готовности:
- пользователь может пройти полный MVP flow.

---

## Этап 4 — History

Что делается:
- local storage
- case list
- delete case
- open case

Что нельзя делать раньше времени:
- добавлять sync между устройствами;
- добавлять аккаунты;
- добавлять database;
- добавлять расширенный поиск или фильтры.

Зависимости:
- этап начинается после рабочего core flow;
- структура кейса должна быть стабильной;
- сохранение не должно ломать безопасные состояния и warning.

Критерий готовности:
- история переживает reload страницы.

---

## Этап 5 — Polish

Что делается:
- accessibility
- mobile UX
- edge cases
- warning texts
- validation
- loading optimization

Что нельзя делать раньше времени:
- расширять scope MVP;
- добавлять OCR;
- добавлять PDF parser;
- добавлять backend;
- добавлять auth;
- добавлять sync;
- добавлять future features вместо стабилизации MVP.

Зависимости:
- этап начинается после scaffold, UI skeleton, core logic и history;
- все основные пользовательские состояния должны уже существовать;
- polish должен улучшать MVP, а не менять его границы.

Критерий готовности:
- MVP стабилен и готов к demo.

## Общие запреты до готовности этапов

- Не начинать AI logic до готового scaffold и UI skeleton.
- Не начинать history до прохождения полного MVP flow.
- Не добавлять backend, auth, OCR, PDF parser или sync в рамках MVP.
- Не расширять маршруты под future features до завершения основного сценария.
- Не добавлять сложную архитектуру, если текущий этап не требует ее для готовности.

## Итоговая последовательность

1. Scaffold.
2. UI skeleton.
3. Core logic.
4. History.
5. Polish.

Нарушение порядка допустимо только если сначала обновлены планы и явно объяснена причина изменения.
