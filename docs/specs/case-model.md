# Модель Case

## Что такое Case в LifePilot

Case — это одна жизненная ситуация пользователя, связанная с одним исходным текстом: письмом, документом, уведомлением, договором или описанием проблемы.

Case объединяет исходный текст, категорию, краткое резюме, уровень риска, приоритет, статус, анализ и план действий. В текущем MVP пользователь видит кейсы через локальную историю в браузере, а таблица `public.cases` подготовлена как Supabase schema foundation для будущего database stage.

Этот документ является единственным источником правды для текущей структуры данных Case, статусов кейса и жизненного цикла кейса. Другие specs и architecture-документы должны ссылаться на него, а не дублировать альтернативные списки статусов или полей.

Будущая target schema для user-owned Supabase storage описана отдельно в [supabase-schema-v1.md](./supabase-schema-v1.md). Она не меняет Current MVP и не применяет migration без утвержденного implementation plan.

## Зачем нужна модель Case

Модель Case нужна, чтобы:

- хранить одну ситуацию как цельный объект, а не как набор разрозненных экранных данных;
- связать исходный текст, анализ, риск, приоритет и план действий;
- сохранить понятную форму данных между `localStorage`, TypeScript-типами и таблицей `public.cases`;
- не смешивать пользовательский UI-flow с подготовительным Supabase schema/client foundation.

## LocalStorage `StoredCase`

`StoredCase` — это локальная TypeScript-форма кейса, которая используется пользовательским MVP-flow через `localStorage`.

`StoredCase` хранится в:

- `lifepilot.currentCase` — текущий кейс для экранов анализа, результата и черновика;
- `lifepilot.caseHistory` — локальная история последних кейсов.

Локальный `StoredCase` использует имена полей, удобные для frontend:

| Поле | Назначение | Обязательность |
| --- | --- | --- |
| `id` | Локальный идентификатор кейса | Обязательное |
| `sourceText` | Исходный текст пользователя | Обязательное |
| `category` | Категория, определенная локальным анализом | Необязательное |
| `riskLevel` | Уровень риска, определенный локальными правилами | Необязательное |
| `analysis` | Частичный или полный локальный результат анализа | Необязательное |
| `status` | Статус кейса, совместимый с `CaseStatus`, или legacy-строка | Необязательное |
| `createdAt` | Дата создания, если она сохранена | Необязательное |
| `updatedAt` | Дата последнего обновления, если она сохранена | Необязательное |

`StoredCase` является рабочей формой для UI текущего MVP. Он не содержит auth session, server user id, Supabase user id, платежные данные, файлы или серверные токены.

## Supabase `SupabaseCaseRow`

`SupabaseCaseRow` — это frontend-тип строки таблицы `public.cases`. Он описывает форму данных, которую должен использовать будущий Supabase database layer.

`SupabaseCaseRow` использует имена полей базы данных:

- `source_text` вместо `sourceText`;
- `risk_level` вместо `riskLevel`;
- `priority_level` вместо `analysis.priorityLevel`;
- `deadline_status` вместо `analysis.deadlineStatus`;
- `action_plan` вместо `analysis.actionPlan`.

`readSupabaseCases()` существует как подготовительная функция приведения `SupabaseCaseRow` к `StoredCase[]`. В текущем MVP anon `SELECT` для `public.cases` не разрешен: migration включает RLS, но не добавляет SELECT policy. Поэтому функция не является рабочим источником данных пользовательского flow и не записывает данные в Supabase.

## Таблица `public.cases`

Таблица `public.cases` существует в Supabase и описана миграцией `supabase/migrations/20260528000000_initial_lifepilot_schema.sql`.

| Поле | Назначение | Тип | Обязательность | Кто заполняет |
| --- | --- | --- | --- | --- |
| `id` | Уникальный идентификатор кейса | `uuid` | Обязательное | Supabase |
| `title` | Краткое название или заголовок кейса | `text` | Nullable | Система |
| `category` | Категория ситуации, определенная локальным анализом | `text` | Nullable | Система |
| `source_text` | Исходный текст письма, документа или описания ситуации | `text` | Обязательное | Пользователь |
| `summary` | Краткое резюме ситуации | `text` | Nullable | Система |
| `risk_level` | Уровень риска кейса | `text` | Nullable | Система |
| `priority_level` | Уровень приоритета кейса | `text` | Nullable | Система |
| `status` | Текущий статус кейса | `text` | Nullable | Система |
| `deadline_status` | Статус найденного срока | `text` | Nullable | Система |
| `action_plan` | План действий по кейсу | `jsonb` | Nullable | Система |
| `analysis` | Сохраненный результат анализа | `jsonb` | Nullable | Система |
| `created_at` | Дата создания записи | `timestamptz` | Nullable, создается автоматически | Supabase |
| `updated_at` | Дата последнего изменения записи | `timestamptz` | Nullable, создается автоматически | Supabase |

## Жизненный цикл Case

Жизненный цикл Case в текущем MVP использует технические статусы, которые сохраняются в локальном кейсе и могут быть представлены в поле `status` таблицы `public.cases`.

1. `new` — кейс создан или открыт как fallback без актуального анализа.
2. `analyzed` — кейс получил анализ, риск, резюме или другие рассчитанные данные.
3. `action-required` — пользователю нужно вручную проверить риск, срок или план действий.
4. `waiting` — кейс ожидает срока, ответа или внешнего шага без высокого риска.
5. `completed` — по текущим правилам нет дальнейших обязательных шагов.

Эти значения являются каноническими для текущей документации. Старые русскоязычные статусы могут встречаться только в локальных данных прошлых версий и должны рассматриваться как legacy fallback.

## Граница текущего MVP

Текущий пользовательский UI работает local-first через `localStorage`.

Supabase foundation layer уже подготовлен частично:

- `lib/supabase-client.ts` создает единый browser-safe Supabase client;
- `lib/supabase-cases.ts` содержит подготовительную функцию `readSupabaseCases()`;
- `supabase/migrations/20260528000000_initial_lifepilot_schema.sql` создает таблицу `public.cases` и включает RLS;
- SELECT policy для anon role сейчас отсутствует, поэтому browser anon client не может читать `public.cases` как рабочий источник данных.

`readSupabaseCases()` пока не является основным пользовательским flow. Экраны создания, результата, истории и детального просмотра продолжают работать через `localStorage`.

## Что пока не входит в MVP

- auth;
- личные аккаунты;
- запись кейсов в Supabase из UI;
- удаление кейсов из Supabase;
- real-time sync;
- сложные права доступа.
