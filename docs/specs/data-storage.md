# Хранение данных LifePilot

## Общий подход

LifePilot хранит данные вокруг пользовательских кейсов: писем, документов и ситуаций. MVP не требует сложной базы данных, аккаунтов или синхронизации.

На первом этапе достаточно локального хранения, если оно поддерживает:

- историю обработанных кейсов;
- сохранение объяснения;
- сохранение плана действий;
- сохранение немецкого ответа;
- базовые настройки пользователя.

Данные должны храниться минимально и понятно. LifePilot работает с чувствительной информацией, поэтому лишние данные собирать нельзя.

## Кейс

Кейс — основная сущность MVP. Это сохраненная пользовательская ситуация, построенная вокруг одного исходного текста: письма, документа или описания проблемы.

Кейс объединяет:

- исходный текст;
- категорию;
- анализ;
- объяснение;
- план действий;
- немецкий ответ;
- статус;
- историю важных изменений.

Кейс нужен, чтобы пользователь видел не разрозненные ответы, а единый результат, к которому можно вернуться позже.

## Жизненный цикл кейса

В MVP кейс проходит такой жизненный цикл:

1. `new` — кейс создан или открыт как fallback без актуального анализа.
2. `analyzed` — система выделила смысл, факты, риски и требования.
3. `action-required` — пользователю нужно вручную проверить риск, срок или план действий.
4. `waiting` — кейс ожидает срока, ответа или внешнего шага без высокого риска.
5. `completed` — по текущим правилам нет дальнейших обязательных шагов.

Защитные статусы:

- `требует уточнения` — данных недостаточно для надежного результата;
- `высокий риск` — ситуация может требовать профессиональной консультации.

Защитные статусы могут дополнять основной статус и не создают отдельный пользовательский сценарий.

## Данные кейса

Для кейса нужно хранить:

- идентификатор;
- название;
- категорию;
- исходный текст;
- дату создания;
- дату последнего изменения;
- статус;
- защитный статус, если он есть;
- уровень риска: `low`, `medium` или `high`;
- короткое объяснение риска;
- краткое резюме;
- найденные сроки;
- найденные суммы;
- найденные требования;
- предупреждения;
- признак необходимости немецкого ответа;
- пользовательские заметки, если они появятся.

Категории MVP:

- жильё;
- банк;
- страховка;
- госорган;
- работа;
- другое.

В интерфейсе категории показываются как: `Жильё`, `Банк`, `Страховка`, `Госорган`, `Работа`, `Другое`. Если старый сохраненный кейс не содержит категорию, система должна считать его категорией `Другое`.

## Действия пользователя с кейсом

В MVP пользователь может:

- создать кейс;
- вставить или заменить исходный текст до анализа;
- выбрать категорию;
- запросить анализ;
- посмотреть объяснение;
- посмотреть план действий;
- сгенерировать немецкий ответ;
- скопировать немецкий ответ;
- сохранить кейс;
- открыть сохраненный кейс из истории.
- открыть detail view сохраненного кейса по `id` без изменения текущего кейса.
- искать, фильтровать и сортировать историю локально без изменения сохраненных данных.

Дополнительные действия с историей кейсов относятся к ограничениям, описанным в `../plans/mvp-scope.md`.

## Объяснение

Для объяснения нужно хранить:

- краткое резюме;
- простое объяснение;
- список важных фактов;
- список требований к пользователю;
- список неясных мест;
- предупреждения;
- уровень уверенности, если он используется в интерфейсе.

Объяснение должно быть связано с конкретным кейсом и исходным текстом.

В текущем MVP список важных фактов хранится внутри локального результата анализа `analysis.extractedData`. В него входят тип документа, организация, номер дела, сроки, сумма, контактные данные, последствия и признаки близкого срока. История должна сохранять этот объект вместе с кейсом, чтобы открытый из истории результат показывал те же факты без повторного ввода текста.

План действий текущего MVP хранится внутри `analysis.actionPlan` как массив коротких шагов. Он формируется локальным Action Plan Engine из `riskLevel`, `analysis.priorityLevel` и `analysis.deadlineStatus`. История должна сохранять этот массив вместе с анализом, чтобы открытый из истории кейс показывал тот же план действий.

Приоритет текущего MVP хранится внутри `analysis.prioritySummary` и `analysis.priorityLevel`. Эти поля сохраняются вместе с локальным анализом в `lifepilot.currentCase` и `lifepilot.caseHistory`, поэтому история открывает сохраненный priority-результат из localStorage. Если старый кейс не содержит priority-полей, экран результата должен открываться без ошибки и может пересчитать локальный анализ из сохраненного исходного текста.

Статус срока текущего MVP хранится внутри `analysis.deadlineStatus`, `analysis.daysRemaining` и `analysis.deadlineMessage`. Эти поля сохраняются вместе с локальным анализом и используются для блока `Статус срока` на экране результата.

Статус кейса текущего MVP хранится внутри `analysis.status` как `CaseStatus`: `new`, `analyzed`, `action-required`, `waiting` или `completed`. Он вычисляется локально после анализа на основе найденного срока, уровня риска и наличия `analysis.actionPlan`. Top-level поле `status` у сохраненного кейса должно дублировать `analysis.status`, чтобы история могла быстро восстановить состояние. Старые русскоязычные статусы из прошлых локальных записей нормализуются через fallback и не требуют миграции backend, auth или database.

## План действий

Для плана действий нужно хранить:

- список шагов;
- порядок шагов;
- срочный первый шаг;
- список нужных документов или данных;
- срок выполнения, если он найден;
- рекомендацию обратиться к специалисту, если она есть.

В MVP шаги плана хранятся как часть кейса, без отдельного модуля управления задачами.

Action Plan Engine не создает задачи, напоминания или backend-сущности. Он только сохраняет 3-5 текстовых шагов внутри локального анализа.

## Немецкий ответ

Для немецкого ответа нужно хранить:

- текст черновика;
- выбранный тон;
- адресата, если он известен;
- тему письма, если она сгенерирована;
- плейсхолдеры для личных данных;
- предупреждение перед отправкой, если оно нужно.

Система хранит только черновик ответа. Факт реальной отправки письма не является частью данных MVP.

## Настройки

Для MVP достаточно хранить:

- язык объяснений;
- предпочитаемый тон немецкого ответа;
- уровень детализации объяснений;
- согласие или отказ от сохранения истории;
- базовые параметры приватности.

Настройки не должны превращаться в сложную конфигурацию. Значения по умолчанию должны подходить большинству пользователей.

## История действий

История в MVP фиксирует не все действия пользователя, а только важные события внутри кейса:

- кейс создан;
- кейс проанализирован;
- объяснение создано;
- план действий создан;
- немецкий ответ создан;
- кейс изменил статус на высокий риск или требует уточнения.

Эта история нужна для восстановления контекста, а не для аналитики поведения.

## Локальное хранение

Локальное хранение подходит для MVP.

Преимущества:

- меньше инфраструктуры;
- быстрее запуск первой версии;
- данные остаются на устройстве пользователя;
- проще объяснить приватность.

Ограничения:

- нет синхронизации между устройствами;
- есть риск потери данных при удалении приложения или очистке браузера;
- сложнее работать с большими документами;
- развитие работы с историей нужно сверять с `../plans/mvp-scope.md`.

## Локальное хранение текущего рабочего MVP

В минимальном рабочем MVP используется только браузерный `localStorage`.

В `localStorage` сейчас находятся:

- текущий кейс;
- локальная история последних кейсов;
- исходный текст;
- категорию;
- рассчитанный уровень риска;
- статус кейса `CaseStatus`;
- дату последнего обновления.

История текущего MVP хранится в `localStorage` и ограничена последними 10 кейсами. Каждая запись истории должна хранить категорию кейса и показывать ее в карточке истории. Очистка истории удаляет только список прошлых кейсов в браузере.

Поиск, фильтр и сортировка истории работают только на клиенте поверх уже загруженного массива `lifepilot.caseHistory`. Эти настройки не сохраняются в `localStorage` и не требуют backend, auth, database или AI API. Поиск должен учитывать title, preview, organization, documentType и найденные keywords. Фильтры используют сохраненные `analysis.status` и `analysis.priorityLevel`, а для старых записей без этих полей интерфейс показывает `Nicht gefunden` и не ломает страницу.

Dashboard на главной странице читает `lifepilot.caseHistory` и считает только локальную статистику: всего кейсов, требуют действия, высокий риск, в ожидании и завершено. Блок `Последний кейс` показывает preview, статус, priority и дату создания. Если `createdAt` отсутствует в старой записи, интерфейс использует `updatedAt`; если данных нет или они невалидны, показывает `Nicht gefunden`. Dashboard не сохраняет агрегаты отдельно и не требует backend, auth, database или AI API.

Экран просмотра сохраненного кейса `/history/[caseId]` читает только `lifepilot.caseHistory`, ищет запись по `id` и показывает сохраненные поля анализа. Если запись не найдена, экран показывает безопасное empty state и ссылку назад в историю. Если старый кейс не содержит новых полей анализа, интерфейс показывает `Nicht gefunden` вместо пустых или ошибочных значений.

Демонстрационный результат анализа может быть сформирован на клиенте из сохраненного текста и не требует backend, database или внешнего сервиса.

## Supabase foundation layer

В проекте подготовлен базовый browser-safe клиент Supabase в `lib/supabase-client.ts`.

Этот слой нужен только как архитектурная основа для будущего database stage. В текущем MVP он не заменяет `localStorage`, не читает и не записывает кейсы, не создает auth-сессию и не предполагает наличие таблиц.

Правила текущего этапа:

- `localStorage` остается единственным рабочим хранилищем кейсов MVP;
- Supabase-клиент может использовать только публичные browser-переменные окружения `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`;
- отсутствие Supabase-переменных должно давать безопасную ошибку только в development;
- production-интерфейс не должен показывать пользователю технические детали конфигурации;
- до появления database schema нельзя добавлять запросы к таблицам, auth-flow, миграции, storage buckets или синхронизацию истории.

Тип базы данных в foundation layer намеренно пустой. Таблицы, связи и row-типы должны появиться только после утверждения database schema.

## Границы хранения текущего MVP

В `localStorage` сейчас не должны находиться:

- auth session;
- server user id;
- Supabase user id;
- платежные данные;
- Stripe customer id;
- subscription status;
- файлы, PDF или изображения;
- данные автоматической отправки писем;
- серверные токены;
- скрытая аналитика поведения пользователя.

Текущий подход ограничен локальным браузером. Данные не доступны на другом устройстве, могут исчезнуть при очистке браузера и не имеют серверной резервной копии. Поэтому `localStorage` подходит для MVP, но не является production-хранилищем для долгосрочной работы с важными документами.

## Приватность

LifePilot может обрабатывать письма, договоры, личные данные и финансовую информацию.

Базовые требования:

- хранить только то, что нужно для кейса;
- не сохранять историю без понятного согласия пользователя;
- предусмотреть понятное управление сохранением истории;
- явно предупреждать о чувствительных данных;
- не передавать данные внешним сервисам без объяснения пользователю;
- не использовать личные документы для посторонних целей.
