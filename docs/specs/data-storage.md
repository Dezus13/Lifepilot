# Хранение данных LifePilot

## Общий подход

LifePilot хранит данные вокруг пользовательских кейсов: писем, документов и ситуаций. Рабочий пользовательский flow MVP не требует сложной базы данных, аккаунтов или синхронизации.

На первом этапе достаточно локального хранения, если оно поддерживает:

- историю обработанных кейсов;
- сохранение объяснения;
- сохранение плана действий.

Данные должны храниться минимально и понятно. LifePilot работает с чувствительной информацией, поэтому лишние данные собирать нельзя.

## Кейс

Кейс — основная сущность MVP. Это сохраненная пользовательская ситуация, построенная вокруг одного исходного текста: письма, документа или описания проблемы.

Кейс объединяет:

- исходный текст;
- категорию;
- анализ;
- объяснение;
- план действий;
- статус;
- историю важных изменений.

Кейс нужен, чтобы пользователь видел не разрозненные ответы, а единый результат, к которому можно вернуться позже.

## Жизненный цикл кейса

Канонические статусы и жизненный цикл Case описаны в [case-model.md](./case-model.md). Этот документ не дублирует список статусов, чтобы не создавать разные источники правды.

## Данные кейса

Для кейса нужно хранить:

- идентификатор;
- название;
- категорию;
- исходный текст;
- дату создания, если она сохранена;
- дату последнего изменения, если она сохранена;
- статус;
- защитное предупреждение, если оно есть;
- уровень риска: `low`, `medium` или `high`;
- короткое объяснение риска;
- краткое резюме;
- найденные сроки;
- найденные суммы;
- найденные требования;
- предупреждения;
- пользовательские заметки, если они появятся.

Допустимые значения `category` в типе Case:

- жильё;
- банк;
- страховка;
- госорган;
- работа;
- документы;
- другое.

В текущем UI `/case/new` нет ручного выбора категории. Пользователь вводит только исходный текст, а категория определяется локально через `createLocalAnalysis()` на основе правил анализа. Текущий локальный классификатор создает категории `Жильё`, `Страховка`, `Работа`, `Документы` или `Другое`. Тип данных также допускает `Банк` и `Госорган` для совместимости со старыми или внешними данными, но текущий локальный анализ не должен описываться как гарантированно создающий эти категории. Если старый сохраненный кейс не содержит категорию, система должна считать его категорией `Другое`.

## Действия пользователя с кейсом

В MVP пользователь может:

- создать кейс;
- вставить или заменить исходный текст до анализа;
- создать кейс на основе текста без ручного выбора категории в текущем UI;
- запросить анализ;
- посмотреть объяснение;
- посмотреть план действий;
- открыть демонстрационный немецкий черновик текущего нейтрального потока;
- открыть сохраненный кейс из истории;
- открыть detail view сохраненного кейса по `id` без изменения текущего кейса;
- искать, фильтровать и сортировать историю локально без изменения сохраненных данных.

Дополнительные действия с историей кейсов относятся к ограничениям, описанным в `../plans/active/mvp-scope.md`.

## Объяснение

Для объяснения нужно хранить:

- краткое резюме;
- простое объяснение;
- список важных фактов;
- список требований к пользователю;
- список неясных мест;
- предупреждения;
- уровень уверенности, если он используется в интерфейсе.

Объяснение должно быть связано с конкретным кейсом и исходным текстом.

В текущем MVP список важных фактов хранится внутри локального результата анализа `analysis.extractedData`. В него входят тип документа, организация, номер дела, сроки, сумма, контактные данные, последствия и признаки близкого срока. История должна сохранять этот объект вместе с кейсом, чтобы открытый из истории результат показывал те же факты без повторного ввода текста.

План действий текущего MVP хранится внутри `analysis.actionPlan` как массив коротких шагов. Он формируется локальным Action Plan Engine из `riskLevel`, `analysis.priorityLevel` и `analysis.deadlineStatus`. История должна сохранять этот массив вместе с анализом, чтобы открытый из истории кейс показывал тот же план действий.

Приоритет текущего MVP хранится внутри `analysis.prioritySummary` и `analysis.priorityLevel`. Эти поля сохраняются вместе с локальным анализом в `lifepilot.currentCase` и `lifepilot.caseHistory`, поэтому история открывает сохраненный priority-результат из localStorage. Если старый кейс не содержит priority-полей, экран результата должен открываться без ошибки и может пересчитать локальный анализ из сохраненного исходного текста.

Статус срока текущего MVP хранится внутри `analysis.deadlineStatus`, `analysis.daysRemaining` и `analysis.deadlineMessage`. Эти поля сохраняются вместе с локальным анализом и используются для блока `Статус срока` на экране результата.

Статус кейса текущего MVP хранится внутри `analysis.status` и top-level поля `status`. Допустимые значения статуса определены в [case-model.md](./case-model.md). Top-level поле `status` у сохраненного кейса должно дублировать `analysis.status`, чтобы история могла быстро восстановить состояние. Старые русскоязычные статусы из прошлых локальных записей нормализуются через fallback и не требуют миграции backend, auth или database.

## План действий

Для плана действий нужно хранить:

- список шагов;
- порядок шагов;
- срочный первый шаг;
- список нужных документов или данных;
- срок выполнения, если он найден;
- рекомендацию обратиться к специалисту, если она есть.

В MVP шаги плана хранятся как часть кейса, без отдельного модуля управления задачами.

Action Plan Engine не создает задачи, напоминания или backend-сущности. Он только сохраняет 3-5 текстовых шагов внутри локального анализа.

## Немецкий ответ

В текущем MVP немецкий черновик не хранится как отдельное поле `StoredCase` и не сохраняется в `lifepilot.caseHistory`.

Экран `/case/draft` читает `lifepilot.currentCase`, использует категорию и risk level как контекст и показывает демонстрационный нейтральный текст письма. Тон ответа не является отдельным пользовательским выбором. Будущий пользовательский выбор тона или сохранение текста черновика должны быть добавлены только после обновления specs и UI-плана.

Факт реальной отправки письма не является частью данных MVP.

## Настройки

В текущем рабочем MVP экран `/settings/safety` не сохраняет пользовательские настройки. Он показывает правила безопасности, ограничение ответственности и напоминание о ручной проверке немецкого черновика.

В `localStorage` текущего MVP не нужно хранить язык объяснений, уровень детализации, выбор тона, согласие на историю или другие пользовательские preference values.

Если будущая версия добавит реальные настройки, сначала нужно обновить specs и UI-план, а затем явно описать ключи хранения, значения по умолчанию и поведение старых локальных данных.

## История действий

История в MVP фиксирует не все действия пользователя, а только важные события внутри кейса:

- кейс создан;
- кейс проанализирован;
- объяснение создано;
- план действий создан;
- пользователь открыл демонстрационный немецкий черновик;
- кейс получил предупреждение о высоком риске или недостаточном контексте.

Эта история нужна для восстановления контекста, а не для аналитики поведения.

## Локальное хранение

Локальное хранение подходит для MVP.

Преимущества:

- меньше инфраструктуры;
- быстрее запуск первой версии;
- данные остаются на устройстве пользователя;
- проще объяснить приватность.

Ограничения:

- нет синхронизации между устройствами;
- есть риск потери данных при удалении приложения или очистке браузера;
- сложнее работать с большими документами;
- развитие работы с историей нужно сверять с `../plans/active/mvp-scope.md`.

## Локальное хранение текущего рабочего MVP

В минимальном рабочем MVP используется только браузерный `localStorage`.

В `localStorage` сейчас находятся:

- текущий кейс;
- локальная история последних кейсов;
- исходный текст;
- категорию;
- рассчитанный уровень риска;
- статус кейса `CaseStatus`;
- дату последнего обновления.

История текущего MVP хранится в `localStorage` как локальный массив кейсов. Новые записи добавляются в начало истории, а очистка истории удаляет только список прошлых кейсов в браузере. Текущая реализация не ограничивает историю последними 10 кейсами, поэтому документация текущего MVP не должна описывать такой лимит как реализованное поведение.

Поиск, фильтр и сортировка истории работают только на клиенте поверх уже загруженного массива `lifepilot.caseHistory`. Эти настройки не сохраняются в `localStorage` и не требуют backend, auth, database или AI API. Поиск должен учитывать title, preview, organization, documentType и найденные keywords. Фильтры используют сохраненные `analysis.status` и `analysis.priorityLevel`, а для старых записей без этих полей интерфейс показывает `Nicht gefunden` и не ломает страницу.

Dashboard на главной странице читает `lifepilot.caseHistory` и считает только локальную статистику: всего кейсов, требуют действия, высокий риск, в ожидании и завершено. Блок `Последний кейс` показывает preview, статус, priority и дату создания. Если `createdAt` отсутствует в старой записи, интерфейс использует `updatedAt`; если данных нет или они невалидны, показывает `Nicht gefunden`. Dashboard не сохраняет агрегаты отдельно и не требует backend, auth, database или AI API.

Экран просмотра сохраненного кейса `/history/[caseId]` читает только `lifepilot.caseHistory`, ищет запись по `id` и показывает сохраненные поля анализа. Если запись не найдена, экран показывает безопасное empty state и ссылку назад в историю. Если старый кейс не содержит новых полей анализа, но содержит `sourceText`, интерфейс может пересчитать локальный анализ на клиенте. Если конкретный факт отсутствует даже после пересчета, интерфейс показывает `Nicht gefunden` вместо пустых или ошибочных значений.

Демонстрационный результат анализа может быть сформирован на клиенте из сохраненного текста и не требует backend, database или внешнего сервиса.

## Supabase foundation layer

В проекте подготовлен базовый browser-safe клиент Supabase в `lib/supabase-client.ts`.

Также существует подготовительный модуль `lib/supabase-cases.ts`. Функция `readSupabaseCases()` описывает будущий путь приведения строк `public.cases` к формату `StoredCase[]` и безопасно возвращает пустой массив, если Supabase не настроен, недоступен, вернул ошибку или чтение запрещено политиками доступа.

Этот слой нужен как инфраструктурная подготовка к будущему database stage. В текущем MVP он не заменяет `localStorage`, не подключен к пользовательскому flow, не записывает кейсы, не создает auth-сессию и не запускает синхронизацию истории.

Принято решение использовать hosted Supabase project. Локальная Supabase через Docker в текущем MVP не используется и не является обязательной частью development flow.

Правила текущего этапа:

- `localStorage` остается единственным рабочим хранилищем кейсов в пользовательском UI;
- hosted Supabase подготовлен как schema/client foundation для таблицы `public.cases`;
- Supabase-клиент может использовать только публичные browser-переменные окружения `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`;
- `.env.local` должен содержать `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` для подключения к hosted Supabase project;
- secret keys, service role keys и приватные токены нельзя использовать на frontend;
- отсутствие Supabase-переменных должно давать безопасную ошибку только в development;
- production-интерфейс не должен показывать пользователю технические детали конфигурации;
- migration file `supabase/migrations/20260528000000_initial_lifepilot_schema.sql` создан только как schema foundation для будущего hosted Supabase stage;
- migration включает RLS для `public.cases`, но SELECT policy для anon role сейчас отсутствует, поэтому browser anon client не может читать таблицу как рабочий источник данных.

Тип базы данных в frontend foundation layer описывает форму таблицы `public.cases`. Связи с пользователями, auth access rules и SELECT policy должны появиться только после утверждения database/auth stage.

### Таблица `public.cases`

В Supabase существует таблица `public.cases`. Ее каноническая структура описана в [case-model.md](./case-model.md), а миграция находится в `supabase/migrations/20260528000000_initial_lifepilot_schema.sql`.

Текущий TypeScript-тип `SupabaseCaseRow` должен совпадать со структурой из [case-model.md](./case-model.md). `readSupabaseCases()` содержит подготовленный select-запрос к `public.cases`, но без SELECT policy для anon role этот запрос не является рабочим источником данных. UI пока не использует результат чтения.

Переход от локального MVP к hosted Supabase должен идти постепенно по направлению `localStorage` -> `public.cases`:

1. сначала перенести case history в Supabase как дополнительный источник хранения;
2. затем сохранять новые cases в Supabase без отключения локального fallback;
3. затем читать историю из Supabase, сохраняя безопасное поведение при недоступности сервиса.

## Границы хранения текущего MVP

В `localStorage` сейчас не должны находиться:

- auth session;
- server user id;
- Supabase user id;
- платежные данные;
- Stripe customer id;
- subscription status;
- файлы, PDF или изображения;
- данные автоматической отправки писем;
- серверные токены;
- скрытая аналитика поведения пользователя.

Текущий подход ограничен локальным браузером. Данные не доступны на другом устройстве, могут исчезнуть при очистке браузера и не имеют серверной резервной копии. Поэтому `localStorage` подходит для MVP, но не является production-хранилищем для долгосрочной работы с важными документами.

## Приватность

LifePilot может обрабатывать письма, договоры, личные данные и финансовую информацию.

Базовые требования:

- хранить только то, что нужно для кейса;
- не сохранять историю без понятного согласия пользователя;
- предусмотреть понятное управление сохранением истории;
- явно предупреждать о чувствительных данных;
- не передавать данные внешним сервисам без объяснения пользователю;
- не использовать личные документы для посторонних целей.
