# Пользовательский поток LifePilot

## Назначение файла

Этот документ описывает только линейный MVP-сценарий. Расширенные сценарии, альтернативные ветки и будущие функции не входят в этот сценарий и должны проверяться через `../plans/mvp-scope.md`.

## Единый MVP-сценарий

Пользователь проходит один основной путь:

1. Открывает LifePilot.
2. Начинает новый кейс.
3. Вставляет текст письма, документа или ситуации.
4. Выбирает категорию.
5. Указывает, нужен ли немецкий ответ.
6. Запускает анализ.
7. Получает анализ исходного текста.
8. Получает объяснение на русском языке.
9. Получает план действий.
10. Получает немецкий ответ.
11. Сохраняет кейс.
12. Видит сохраненный кейс в истории.

## Минимальный рабочий сценарий текущей реализации

Для первого рабочего MVP используется сокращенный сценарий без backend, auth, database и настоящей AI-логики:

1. Пользователь открывает страницу `Новый кейс`.
2. Вставляет текст письма, документа или ситуации в textarea.
3. Выбирает категорию: `Жильё`, `Банк`, `Страховка`, `Госорган`, `Работа` или `Другое`.
4. Нажимает `Анализировать`.
5. Система сохраняет исходный текст и категорию текущего кейса в `localStorage` браузера.
6. Пользователь переходит на страницу `Анализ`.
7. Страница `Анализ` показывает состояние загрузки около 2 секунд: чтение текста, оценка риска, подготовка результата.
8. После loading пользователь автоматически переходит на страницу `Результат`.
9. Страница `Результат` показывает категорию, краткий анализ, уровень риска и рекомендации на основе локального демонстрационного результата.
10. Страница `Черновик` показывает пример немецкого ответа для ручной проверки.
11. Главная страница показывает dashboard-статистику по локальной истории и блок `Последний кейс`.
12. Страница `История` показывает последние локальные кейсы с категориями и позволяет открыть результат выбранного кейса.
13. Пользователь может открыть сохраненный кейс на `/history/[caseId]`, чтобы посмотреть detail view без backend, auth, database или AI API.
14. Пользователь может искать, фильтровать и сортировать историю локально в браузере.

Этот сценарий является техническим срезом для проверки навигации, сохранения текущего текста, категории, истории кейсов и mobile-first интерфейса.

Если поле на странице `Новый кейс` пустое, текст не сохраняется и анализ не запускается. Пользователь видит короткое предупреждение и остается на этом же экране.

Если сохраненный ранее кейс не содержит категорию, интерфейс показывает категорию `Другое`.

## Линейная цепочка экранов

Основной путь проходит через экраны:

1. Главная.
2. Экран вставки текста.
3. Экран результата анализа.
4. Экран генерации ответа.
5. История запросов.

Настройки доступны как вспомогательный экран, но не являются обязательным шагом основного сценария.

## Действия на каждом шаге

### Главная

Назначение: начать новый кейс или открыть историю.

Пользователь:

- нажимает действие для нового кейса;
- видит статистику по локальной истории: всего кейсов, требуют действия, высокий риск, в ожидании, завершено;
- видит блок `Последний кейс` с названием, статусом, priority и датой создания;
- может открыть последний сохраненный кейс;
- может перейти в настройки.

Если локальная история пуста, главная страница показывает empty state `История пока пуста`. Старые записи без новых полей не ломают dashboard: отсутствующие значения показываются как `Nicht gefunden`.

### Экран вставки текста

Назначение: собрать минимальные данные для создания кейса.

Пользователь:

- вставляет текст;
- выбирает категорию;
- указывает, нужен ли немецкий ответ;
- запускает анализ.

Если текст пустой, система не создает кейс и просит вставить текст.

### Экран результата анализа

Назначение: показать результат обработки кейса.

Пользователь получает:

- анализ исходного текста;
- объяснение простыми словами;
- важные факты;
- предупреждения;
- план действий.

После просмотра результата пользователь переходит к немецкому ответу.

### Экран генерации ответа

Назначение: подготовить немецкий черновик.

Пользователь:

- выбирает тон ответа;
- получает немецкий текст;
- проверяет плейсхолдеры;
- копирует ответ при необходимости;
- сохраняет результат в кейсе.

### История запросов

Назначение: показать сохраненные кейсы.

Пользователь:

- видит сохраненный кейс;
- ищет кейсы по preview, организации, типу документа и ключевым словам;
- фильтрует кейсы по статусу и приоритету;
- сортирует кейсы по дате или важности;
- открывает detail view сохраненного кейса;
- открывает результат;
- может очистить локальную историю;
- возвращается к основному сценарию через новый кейс.

Если после поиска или фильтров ничего не найдено, история показывает empty state `Кейсы не найдены`. Старые кейсы без новых полей анализа остаются доступными, а отсутствующие значения показываются как `Nicht gefunden`.

### Просмотр сохраненного кейса

Назначение: показать сохраненный локальный анализ из истории без изменения текущего кейса.

Пользователь получает:

- preview кейса;
- статус кейса;
- приоритет и краткое резюме;
- статус срока;
- организацию, тип документа, требуемое действие и последствия;
- план действий;
- найденные ключевые слова;
- preview исходного текста.

Если кейс не найден в `localStorage`, система показывает безопасное empty state и кнопку назад в историю. Если старый кейс не содержит новые поля анализа, экран показывает `Nicht gefunden`.

## Жизненный цикл кейса в сценарии

В рамках MVP кейс проходит простой жизненный цикл:

1. `new` — кейс создан или открыт как fallback без актуального анализа.
2. `analyzed` — система получила результат анализа.
3. `action-required` — пользователь должен проверить риск, срок или план действий.
4. `waiting` — кейс ожидает срока, ответа или внешнего шага.
5. `completed` — дальнейших обязательных шагов по текущим правилам нет.

Если данных недостаточно для надежного анализа, кейс получает статус `требует уточнения`, а система показывает, какие данные нужно добавить. Это не отдельная ветка продукта, а защитное состояние внутри основного сценария.
