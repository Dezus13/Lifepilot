# Mobile layout MVP LifePilot

## Назначение документа

Этот документ описывает базовую структуру мобильных экранов LifePilot для MVP. Он не задает техническую реализацию и не описывает frontend-код.

## Общая структура экрана

Каждый мобильный экран состоит из:

- верхней зоны;
- основной прокручиваемой области;
- зоны предупреждений, если они нужны;
- нижней зоны действий;
- системной safe area.

Интерфейс должен оставаться удобным на небольших экранах. Основной сценарий не должен требовать сложной навигации или горизонтального скролла.

## Header

Header нужен для ориентации пользователя.

В header могут быть:

- название текущего шага;
- кнопка назад;
- короткий статус кейса;
- доступ к настройкам, если это уместно;
- индикатор высокого риска, если кейс уже помечен.

Header не должен быть перегружен. В MVP не нужно размещать там длинные объяснения, вторичные действия или полную навигацию.

Для экранов с длинным результатом header может оставаться закрепленным, если это помогает не потерять контекст. При этом он не должен занимать слишком много вертикального места.

## Основная область

Основная область содержит главный контент экрана:

- форму создания кейса;
- прогресс анализа;
- результат анализа;
- план действий;
- немецкий черновик;
- список кейсов;
- настройки безопасности.

Контент строится вертикально. Каждый смысловой блок занимает всю доступную ширину внутри мобильного контейнера.

## Bottom actions

Нижняя зона действий содержит главное действие текущего экрана.

Примеры:

- начать;
- запустить анализ;
- перейти к черновику;
- вернуться к результату.

Правила:

- на экране должен быть один основной CTA;
- вторичные действия не должны конкурировать с основным;
- нижняя зона не должна перекрывать последний блок контента;
- при disabled-состоянии должно быть понятно, что нужно исправить;
- на high-risk экране нижнее действие должно вести к безопасному экрану или назад к результату, а не выглядеть как подтверждение безопасного использования черновика.

## Scroll behavior

Все длинные экраны прокручиваются вертикально.

Правила скролла:

- header и bottom actions могут оставаться видимыми;
- контент должен иметь нижний отступ, чтобы последняя карточка не скрывалась под кнопкой;
- предупреждения должны встречаться до опасного действия;
- немецкий черновик должен прокручиваться вместе с контентом, если он не помещается;
- внутри карточек не должно быть отдельных маленьких скролл-зон, кроме крайней необходимости.

Экран результата анализа может быть длинным. Он должен читаться секциями: резюме, важные факты, предупреждения, план действий, переход к черновику.

## Safe area

Интерфейс должен учитывать системные зоны телефона:

- верхнюю зону камеры и системного статуса;
- нижнюю зону жестов;
- клавиатуру при вводе текста;
- системные отступы при открытии действий.

Кнопки в нижней зоне не должны попадать слишком близко к краю экрана. Поле ввода должно оставаться доступным при открытой клавиатуре.

## Размеры блоков

Размеры описываются на уровне принципов, без технических значений.

Минимальные требования:

- интерактивные элементы достаточно крупные для касания;
- карточки не должны быть слишком плотными;
- поле исходного текста должно позволять читать несколько строк без постоянной прокрутки;
- блок немецкого черновика должен выглядеть как текст письма, а не как маленькое поле;
- warning и danger блоки должны быть заметными, но не занимать весь экран без необходимости;
- список истории должен показывать несколько кейсов на одном экране, если они есть.

## Где показываются warnings

Warnings показываются рядом с решением, на которое они влияют.

Основные места:

- на экране создания кейса, если текст пустой, короткий или неполный;
- на экране анализа, если документ непонятен или идет обработка рискованного текста;
- в результате анализа перед планом действий, если есть срок, сумма, риск или неясность;
- перед немецким черновиком, если он содержит плейсхолдеры;
- на экране немецкого черновика перед ручным использованием текста;
- на отдельном high-risk warning экране, если пользователь открывает предупреждение о риске.

Предупреждение должно быть видно до того, как пользователь нажмет действие, которое может привести к ошибочному использованию результата.

## Где показывается немецкий черновик

Немецкий черновик показывается на отдельном экране после результата анализа.

Структура экрана:

- header с названием экрана и кратким контекстом категории;
- предупреждение о том, что текст является черновиком;
- отображение текущего нейтрального тона без отдельного выбора;
- сам немецкий текст;
- предупреждение о ручной проверке и плейсхолдерах;
- действие возврата к результату.

Если кейс высокий риск, текущий MVP должен явно показать предупреждение и не создавать ощущение безопасного готового ответа. Автоматическая блокировка черновика и template-only режим являются будущей safety-задачей.

## Поведение при клавиатуре

На экране создания кейса поле ввода является главным элементом. При открытой клавиатуре:

- поле ввода должно оставаться видимым;
- кнопка запуска анализа не должна перекрывать текст;
- подсказки об ошибках должны быть рядом с полем;
- пользователь должен иметь возможность закрыть клавиатуру и проверить введенный текст.
