# Design system MVP LifePilot

## Назначение документа

Этот документ фиксирует базовые правила визуальной системы MVP LifePilot перед началом frontend-реализации. Он описывает только интерфейсную структуру и визуальные принципы, без кода, библиотек и технической реализации.

## Общий стиль

Интерфейс LifePilot должен быть спокойным, понятным и mobile-first. Пользователь приходит в приложение с тревожным документом, поэтому дизайн должен снижать нагрузку, а не создавать ощущение сложного профессионального инструмента.

Основной характер интерфейса:

- минимальный;
- светлый;
- спокойный;
- читаемый;
- ориентированный на действие;
- осторожный в предупреждениях;
- без декоративной перегрузки.

## Основные цвета MVP

Цвета описывают смысловые роли, а не конкретные технические токены.

### Базовые цвета

- Фон приложения: очень светлый нейтральный оттенок.
- Основная поверхность: белая или почти белая.
- Вторичная поверхность: мягкий серый фон для разделения блоков.
- Основной текст: почти черный нейтральный цвет.
- Вторичный текст: серый цвет для пояснений и метаданных.
- Разделители: светло-серый цвет с низким контрастом.

### Акцент

Основной акцент должен быть спокойным и доверительным. Он используется для главного действия: создать кейс, запустить анализ, перейти к результату, сохранить.

Акцент не должен доминировать на экране. В MVP важнее читаемость текста и ясность действий, чем яркая визуальная идентичность.

### Состояния

- Safe: зеленый или спокойный положительный оттенок для безопасного состояния, успешного сохранения и подтверждения.
- Warning: желтый или янтарный оттенок для уточнений, неполных данных и осторожности.
- Danger: красный или бордовый оттенок для высокого риска, критичных сроков и действий, которые нельзя делать автоматически.

Цвет состояния всегда должен сопровождаться текстом. Нельзя передавать риск только цветом.

## Типы кнопок

### Primary

Главная кнопка экрана. Используется для одного основного действия:

- начать новый кейс;
- запустить анализ;
- перейти к немецкому черновику;
- сохранить кейс.

На одном экране не должно быть нескольких равнозначных primary-кнопок.

### Secondary

Вторичное действие без сильного визуального веса:

- открыть историю;
- вернуться к результату;
- изменить тон;
- открыть настройки.

### Ghost

Тихое действие внутри блока или в header:

- назад;
- закрыть;
- посмотреть детали;
- изменить ввод.

### Danger

Опасное или ограничивающее действие. В MVP используется редко:

- отказаться от сохранения;
- закрыть несохраненный кейс;
- подтвердить выход из рискованного состояния.

Danger-кнопка не должна выглядеть как основной путь вперед.

### Disabled

Недоступная кнопка показывает, что действие пока невозможно:

- пустой текст;
- слишком короткий текст;
- не выбрана обязательная настройка;
- результат еще формируется.

Рядом или внутри контекста должно быть понятно, почему действие недоступно.

## Карточки

Карточки используются только для смысловых блоков:

- краткое резюме;
- важные факты;
- предупреждение;
- план действий;
- немецкий черновик;
- элемент истории кейсов.

Карточка должна иметь:

- короткий заголовок;
- ясное содержание;
- небольшие внутренние отступы;
- мягкую границу или легкий фон;
- радиус не больше умеренного;
- отсутствие лишней декоративности.

Нельзя вкладывать карточки в карточки. Если нужен сложный результат, он делится на последовательные секции.

## Warning, safe и danger состояния

### Safe

Safe-состояние используется, когда действие завершено или результат можно спокойно использовать после обычной проверки:

- кейс сохранен;
- анализ завершен;
- черновик создан без высокого риска;
- обязательные данные заполнены.

Текст safe-состояния должен быть коротким и не обещать юридическую правильность.

### Warning

Warning-состояние используется, когда нужно внимание пользователя:

- текст неполный;
- есть срок;
- часть данных неясна;
- немецкий ответ содержит плейсхолдеры;
- результат нужно проверить особенно внимательно.

Warning не должен блокировать весь экран, если пользователь может продолжать безопасно.

### Danger

Danger-состояние используется при высоком риске:

- возможный штраф;
- расторжение;
- выселение;
- долг;
- отказ;
- юридически значимый спор;
- AI не уверен в критичном результате.

Danger должен быть заметным, но не паническим. Главная задача - остановить автоматическое использование результата и предложить безопасный следующий шаг.

## Mobile-first принципы

MVP проектируется для телефона.

Основные принципы:

- один главный сценарий на экране;
- один основной CTA внизу или в конце содержимого;
- короткие заголовки;
- текст разбит на небольшие блоки;
- важные предупреждения видны до действия;
- длинные результаты читаются через секции;
- интерактивные элементы достаточно крупные для пальца;
- пользователь всегда понимает, что будет дальше.

Desktop-адаптация не должна менять продуктовую логику MVP. Она может только расширять ширину контейнера и делать чтение удобнее.

## Типографика

Типографика должна поддерживать чтение тревожных и формальных текстов.

Роли текста:

- Заголовок экрана: короткий, ясный, без маркетингового тона.
- Подзаголовок: объясняет состояние или следующий шаг.
- Основной текст: используется для объяснений, плана и предупреждений.
- Мелкий текст: используется для метаданных, дат, статусов и пояснений.
- Немецкий черновик: должен быть читаемым как письмо, с достаточным межстрочным расстоянием.

Не использовать слишком мелкий текст для предупреждений, сроков, сумм и юридически значимых мест.

## Spacing

Отступы должны создавать спокойный ритм.

Базовые правила:

- больше воздуха между крупными смысловыми секциями;
- меньше воздуха внутри связанных элементов;
- одинаковые отступы у однотипных блоков;
- нижняя зона действий не должна перекрывать контент;
- предупреждения не должны слипаться с основным текстом;
- длинный немецкий черновик должен иметь комфортные внутренние отступы.

## Принципы минималистичного интерфейса

LifePilot не должен выглядеть как сложная юридическая система.

Минимализм MVP означает:

- показывать только нужное для текущего шага;
- не перегружать экран пояснениями;
- не использовать декоративные блоки без функции;
- не смешивать много цветов на одном экране;
- не делать несколько равнозначных действий;
- не прятать предупреждения;
- не заставлять пользователя читать длинную инструкцию перед началом;
- оставлять ясный путь: ввод, анализ, результат, черновик, сохранение.

Минималистичный интерфейс не должен скрывать риски. Предупреждения, неопределенность и плейсхолдеры должны быть видимыми.
