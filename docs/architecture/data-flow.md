# Поток данных LifePilot

## Назначение документа

Этот документ описывает движение данных в текущем MVP LifePilot: от создания кейса до результата, истории и детального экрана сохраненного кейса. Документ фиксирует клиентский поток без новой бизнес-логики, backend и auth. Supabase существует только как подготовительный read-only слой и не участвует в пользовательском flow.

## Цель потока данных

Поток данных нужен, чтобы все экраны работали с одним понятным источником состояния и безопасно переживали перезагрузку страницы, пустые данные и старые локальные записи.

Основной сценарий:

1. Пользователь открывает `/case/new` и вставляет текст письма, документа или описания ситуации.
2. После запуска анализа приложение создает локальный объект кейса и сохраняет исходный текст как часть текущего кейса.
3. Текст попадает в локальный анализ на клиенте: приложение извлекает демонстрационные поля, рассчитывает уровень риска, приоритет, статус срока и план действий без обращения к backend.
4. `/case/analyzing` показывает промежуточное состояние и переводит пользователя к результату.
5. `/case/result` читает текущий кейс из локального состояния хранения и показывает сохраненный результат анализа, предупреждения, факты, план действий и действия пользователя.
6. Кейс сохраняется в локальной истории, чтобы пользователь мог вернуться к нему позже из `/history`.
7. `/history/[caseId]` открывает детальный экран сохраненного кейса по `id` из локальной истории, не требуя backend и не меняя database.
8. Supabase уже подготовлен как read-only infrastructure layer для `public.cases`, но текущий UI не вызывает его и не заменяет `localStorage`.

## Текущий поток MVP

### `/case/new`

Экран создания кейса принимает пользовательский текст. В текущем UI нет ручного выбора категории: категория определяется локально через `createLocalAnalysis()` при создании анализа. Пустой текст не должен создавать кейс и не должен запускать анализ.

При успешном запуске создается локальный объект кейса с минимальными полями. Каноническая структура Case описана в [case-model.md](../specs/case-model.md):

- `id`;
- `sourceText`;
- `category`;
- `riskLevel`;
- `status`;
- `analysis`, если локальный анализ уже сформирован;
- `createdAt`;
- `updatedAt`.

Новый кейс становится текущим и записывается в историю последних кейсов.

### `/case/analyzing`

Экран анализа работает как шаг, защищенный состоянием. Он ожидает наличие текущего кейса и исходного текста.

Если данные есть, экран показывает loading-состояние и ведет пользователя к `/case/result`. Если данных нет, сценарий должен безопасно вернуть пользователя к созданию кейса или показать понятное пустое состояние.

### `/case/result`

Экран результата читает текущий кейс из `lifepilot.currentCase`. Он показывает данные, которые уже сохранены внутри кейса: резюме, уровень риска, приоритет, статус срока, найденные факты, план действий и рекомендации.

Если кейс старый и не содержит часть новых полей анализа, экран должен показывать `Nicht gefunden` или безопасно пересчитать локальный анализ из сохраненного `sourceText`.

### `/case/draft`

Экран черновика использует текущий кейс и сохраненный результат анализа как контекст для демонстрационного немецкого ответа. Черновик не означает отправку письма и не фиксирует реальное действие пользователя за пределами приложения.

Если результата нет, экран должен вернуть пользователя к безопасному предыдущему шагу: `/case/result`, если текущий кейс доступен, или `/case/new`, если данные отсутствуют.

### `/history`

Экран истории читает `lifepilot.caseHistory` из `localStorage` и показывает локальный список последних кейсов. Поиск, фильтры и сортировка работают только поверх загруженного массива и не создают отдельные записи в хранилище.

Если история пуста, экран показывает empty state. Старые записи без новых полей должны оставаться видимыми, а отсутствующие значения должны отображаться как `Nicht gefunden`.

### `/history/[caseId]`

Детальный экран истории читает только `lifepilot.caseHistory`, ищет кейс по `id` и показывает сохраненные поля анализа. Этот экран не требует текущего кейса в `lifepilot.currentCase`, не обязан изменять `lifepilot.currentCase` и не должен зависеть от backend.

Если кейс не найден, экран показывает безопасный empty state и действие возврата в историю. Если сохраненный кейс старый или неполный, интерфейс показывает `Nicht gefunden` вместо пустых или ошибочных значений.

## Источники данных

### `localStorage`

В текущем MVP `localStorage` является рабочим источником данных для кейсов.

Основные ключи:

- `lifepilot.currentCase` — текущий кейс для `/case/analyzing`, `/case/result` и `/case/draft`;
- `lifepilot.caseHistory` — локальная история последних кейсов для `/history` и `/history/[caseId]`.

`localStorage` хранит только данные MVP в браузере пользователя. Он не дает синхронизацию между устройствами и не является production-хранилищем для долгосрочной работы с важными документами.

### `.env.local`

`.env.local` используется для локальных переменных окружения, включая публичные Supabase-переменные:

- `NEXT_PUBLIC_SUPABASE_URL`;
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

Файл `.env.local` не должен попадать в git. Даже публичные frontend-переменные не должны превращаться в место хранения секретов.

### Supabase client

Supabase подключен как foundation layer через browser-safe client. В проекте существует таблица `public.cases` и read-only функция `readSupabaseCases()`, которая может прочитать список кейсов через существующий client. Структура Case и допустимые статусы описаны в [case-model.md](../specs/case-model.md).

В текущем пользовательском flow Supabase не используется: экраны создания, результата, истории и детального просмотра продолжают читать и писать только `localStorage`. Supabase-слой не создает auth-flow, не записывает данные, не запускает синхронизацию и не должен ломать локальный flow.

## Решение по Supabase

Текущий источник данных для пользовательского MVP — `localStorage`. Все рабочие сценарии создания кейса, анализа, результата, черновика, истории и детального экрана истории должны продолжать работать локально.

Подготовленный источник данных — hosted Supabase project с таблицей `public.cases`. Сейчас он представлен только типизированным client и read-only функцией `readSupabaseCases()`. Локальная Supabase через Docker и local Supabase URL в текущем MVP не используются.

Fallback-правило: если Supabase недоступен, не настроен или возвращает ошибку, локальный MVP не должен ломаться. `localStorage` остается fallback и рабочим источником данных текущего MVP. Пользовательский поток должен продолжать опираться на `localStorage`, а интерфейс не должен запускать автоматическую миграцию, повторный анализ или отправку данных.

Auth rules, database rules, user ownership и синхронизация истории не меняются на этом шаге. Созданная migration является schema foundation для hosted Supabase stage; подключение пользовательского flow к таблице должно быть отдельным этапом.

## Правила безопасности

- `.env.local` не коммитится.
- Secret keys, service role keys и приватные токены нельзя использовать на frontend.
- Исходный текст пользователя не отправляется автоматически во внешние сервисы.
- Немецкий черновик не отправляется автоматически.
- Пользователь должен вручную проверить результат, предупреждения, сроки, суммы и черновик перед любым внешним действием.
- URL не должен содержать полный исходный текст, личные данные или чувствительный смысл кейса.
- Сохраненные локальные данные должны открываться осторожно: отсутствие поля не считается ошибкой приложения.

## Fallback и error behavior

- Если текущий кейс отсутствует, экраны, защищенные состоянием, должны показывать безопасный fallback или вести пользователя к `/case/new`.
- Если сохраненный кейс не найден, `/history/[caseId]` показывает empty state с возвратом в историю.
- Если отдельное поле анализа отсутствует, интерфейс показывает `Nicht gefunden`.
- Если история пуста, `/history` показывает empty state без создания тестовых данных.
- Старые кейсы из `localStorage` должны открываться безопасно, даже если в них нет новых полей `analysis`, `priorityLevel`, `deadlineStatus` или `status`.
- Отсутствие Supabase-переменных или недоступность Supabase не должны ломать локальный MVP.
- Ошибка чтения `public.cases` через `readSupabaseCases()` должна возвращать пустой массив и не влиять на UI, пока Supabase не подключен к пользовательскому flow.
- Ошибки чтения локальных данных не должны запускать анализ, отправку ответа или создание нового кейса автоматически.

## Роль Supabase в будущем

Supabase может стать основой следующих этапов:

- хранение кейсов в database;
- авторизация пользователей;
- синхронизация между устройствами;
- server-side access control;
- безопасные серверные операции поверх утвержденной schema.

Переход пользовательского flow к Supabase должен быть отдельным архитектурным этапом. До него нельзя добавлять скрытые записи в database, auth-зависимости или автоматическую синхронизацию истории.
