# Frontend-структура MVP LifePilot

## Назначение документа

Этот документ описывает будущую структуру frontend-части LifePilot для MVP без реализации UI, компонентов и бизнес-логики. Он нужен как ориентир перед scaffold, чтобы первые файлы интерфейса не появились случайно и не смешали экраны, общие элементы, хранение и сервисные слои.

Документ не добавляет технологию и не требует создавать перечисленные папки прямо сейчас.

## Общий принцип

Frontend MVP должен быть организован вокруг пользовательского пути:

1. Onboarding.
2. Главный экран.
3. Создание кейса.
4. Анализ документа.
5. Результат анализа.
6. Немецкий черновик.
7. История кейсов.
8. Настройки безопасности.
9. Ошибка.
10. High-risk warning.

Структура должна помогать отделять:

- экраны;
- переиспользуемые UI-блоки;
- feature-модули;
- хранение;
- сервисы;
- типы;
- константы;
- стили.

## Вариант корневой структуры

Если выбранный scaffold использует `app/`, структура может быть такой:

```text
app/
  routes-or-screens/
  shared/
  features/
  storage/
  services/
  hooks/
  constants/
  types/
  styles/
```

Если выбранный scaffold использует `src/`, структура может быть такой:

```text
src/
  pages-or-screens/
  shared/
  features/
  storage/
  services/
  hooks/
  constants/
  types/
  styles/
```

До выбора scaffold нельзя одновременно создавать `app/` и `src/`. Нужен один основной корень, чтобы не получить две конкурирующие архитектуры.

## Pages и screens

Слой screens отвечает за целые экраны MVP.

Ожидаемые экраны:

- onboarding;
- главный экран;
- создание кейса;
- анализ документа;
- результат анализа;
- немецкий черновик;
- история кейсов;
- настройки безопасности;
- экран ошибки;
- high-risk warning.

Screen-слой не должен содержать сложную бизнес-логику. Его задача:

- собрать нужные блоки;
- показать правильное состояние;
- передать пользовательское действие дальше;
- соблюдать mobile-first layout;
- отображать warning, danger и empty состояния.

## Shared components

`shared/` содержит переиспользуемые блоки, которые не принадлежат одной feature.

Примеры shared-блоков:

- общий layout экрана;
- header;
- bottom actions;
- карточка;
- status badge;
- empty state;
- loading state;
- error state;
- warning banner;
- danger banner;
- safe notice;
- список фактов;
- блок плейсхолдеров.

Shared-компоненты не должны знать бизнес-сценарий кейса глубже, чем нужно для отображения переданных данных.

## UI components

`ui/components/` или аналогичный слой содержит базовые элементы интерфейса:

- кнопка;
- поле текста;
- переключатель;
- выбор категории;
- выбор тона;
- секция;
- разделитель;
- бейдж;
- модальное или отдельное предупреждение, если оно нужно scaffold;
- типографические элементы.

UI-компоненты должны быть максимально простыми. Они не должны решать, можно ли генерировать немецкий ответ или является ли кейс high-risk.

## Feature modules

Feature-модули группируют блоки вокруг продуктовых частей MVP.

Минимальные feature-модули:

- `onboarding`;
- `case-creation`;
- `case-analysis`;
- `analysis-result`;
- `german-draft`;
- `case-history`;
- `safety-settings`;
- `risk-warning`.

Каждый feature-модуль может содержать:

- экранные блоки;
- локальные presentation-компоненты;
- локальные состояния отображения;
- адаптацию данных для UI;
- тексты, если они не являются глобальными.

Feature-модуль не должен превращаться в отдельное приложение. Если блок нужен в нескольких feature, его нужно вынести в shared.

## Storage

`storage/` отвечает за frontend-хранение MVP.

В MVP storage нужен для:

- сохраненных кейсов;
- текущего черновика кейса;
- настроек безопасности;
- признака прохождения onboarding;
- разрешения на сохранение истории.

Storage не должен содержать AI-логику, генерацию текста или правила безопасности. Он только сохраняет и возвращает данные в понятной форме.

## Services

`services/` отвечает за внешние или внутренние операции, которые не являются UI.

В MVP возможны сервисные зоны:

- анализ кейса;
- подготовка немецкого черновика;
- сохранение кейса;
- чтение истории;
- работа с настройками.

До появления backend или AI-интеграции сервисы могут быть описаны интерфейсно, но не должны имитировать полноценную бизнес-систему без необходимости.

## Hooks

`hooks/` содержит переиспользуемую frontend-логику отображения и состояния.

Возможные зоны:

- текущее состояние кейса;
- сохранение и чтение истории;
- состояние формы создания кейса;
- состояние анализа;
- состояние копирования немецкого черновика;
- состояние warning и error.

Hooks не должны скрывать сложную бизнес-логику. Если правило важно для продукта, оно должно быть описано в specs или architecture, а не жить только внутри hook.

## Constants

`constants/` хранит стабильные значения MVP:

- категории кейса;
- статусы кейса;
- защитные статусы;
- типы warning;
- типы кнопок;
- маршруты;
- варианты тона немецкого ответа;
- минимальные UI-ограничения.

Константы должны соответствовать документации. Нельзя добавлять новые статусы или категории только потому, что это удобно в UI.

## Types

`types/` хранит frontend-типы данных.

Минимальные типы:

- кейс;
- статус кейса;
- защитный статус;
- результат анализа;
- важный факт;
- предупреждение;
- шаг плана;
- немецкий черновик;
- настройки безопасности;
- route state;
- error state.

Типы должны отражать архитектуру кейса, а не случайную форму одного экрана.

## Styles

`styles/` хранит глобальные правила визуальной системы:

- базовые цвета;
- типографика;
- spacing;
- mobile-first layout;
- safe area;
- состояния warning, safe и danger;
- общие правила карточек и кнопок.

Стили не должны содержать продуктовую логику. Цвет danger показывает риск, но не решает, что кейс рискованный.

## Mobile-first организация

Frontend-структура должна исходить из мобильного сценария.

Правила:

- экран проектируется как вертикальный поток;
- bottom actions должны быть частью layout-слоя;
- предупреждения должны быть выше опасного действия;
- длинные результаты делятся на секции;
- немецкий черновик отображается как отдельный экран;
- история показывает краткие и безопасные previews;
- high-risk warning может быть отдельным экраном или блокирующим состоянием маршрута.

## Что не включать в scaffold MVP

На этапе frontend foundation не нужно создавать:

- сложный state manager без явной необходимости;
- дизайн-токены сверх базового набора;
- отдельный UI-kit как продукт внутри продукта;
- универсальный роутинг для будущих функций;
- слой ролей и прав доступа;
- account/auth структуру;
- папки для OCR, PDF, email, calendar или sync;
- моковые backend-сценарии, которые выглядят как реальные интеграции.
