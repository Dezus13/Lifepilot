# Управление состоянием MVP LifePilot

## Назначение документа

Этот документ описывает, какие данные существуют в приложении, где они живут, как передаются между экранами и какие данные сохраняются постоянно в текущем MVP.

Каноническая структура Case, `StoredCase`, `SupabaseCaseRow`, статусы и жизненный цикл описаны в [../specs/case-model.md](../specs/case-model.md). Этот документ описывает размещение состояния, а не альтернативную модель Case.

## Общий принцип

В MVP не нужен отдельный сложный state manager. Состояние делится на три уровня:

- временное состояние экрана;
- текущий кейс;
- локальная история кейсов.

Временное состояние хранится в React state внутри экранов. Текущий кейс и история сохраняются в `localStorage`, потому что именно они должны переживать переходы между маршрутами и перезагрузку страницы.

## Данные приложения

В приложении существуют следующие группы данных:

- исходный текст пользователя;
- категория кейса, рассчитанная локальным анализом;
- идентификатор кейса;
- дата обновления;
- статус кейса;
- рассчитанный `riskLevel`;
- краткое отображение результата;
- рекомендации по уровню риска;
- немецкий черновик или демонстрационный шаблон;
- список сохраненных кейсов;
- UI-состояния экранов.

В текущем рабочем MVP результат анализа не является отдельной сохраненной сущностью. Он отображается на основе текущего кейса, исходного текста и локального результата `createLocalAnalysis()`, который определяет категорию, риск, приоритет, статус и план действий.

## Временные данные

Временные данные существуют только на конкретном экране:

- текст в textarea до нажатия `Анализировать`;
- текст в textarea до создания кейса;
- inline-warning для пустого текста;
- loading-состояние экрана анализа;
- состояние чтения `localStorage`;
- временное состояние пустого результата или ошибки;
- состояние UI после очистки истории.

Если пользователь обновит страницу до сохранения текущего кейса, временные данные формы могут быть потеряны.

## Постоянные данные MVP

Постоянные данные MVP находятся в `localStorage`:

- `lifepilot.currentCase` — текущий кейс, который открывают экраны анализа и результата;
- `lifepilot.caseHistory` — список последних кейсов для экрана истории.

## Auth/Admin Foundation state

Auth/Admin Foundation реализован и остается отдельным от Case state. Source of truth:

- [auth-admin-foundation-decision-review.md](./auth-admin-foundation-decision-review.md);
- [../specs/auth-spec.md](../specs/auth-spec.md);
- [../specs/admin-spec.md](../specs/admin-spec.md);
- [../specs/security-model.md](../specs/security-model.md).

Auth state не должен смешиваться с Case state.

Auth/Admin Foundation использует следующие состояния:

- `unauthenticated`;
- `authenticating`;
- `authenticated-pending-admin-check`;
- `admin-authorized`;
- `admin-forbidden`;
- `auth-error`.

Эти состояния описывают auth-flow и не являются `CaseStatus`.

Правила состояния:

- Supabase Auth session не хранится в `lifepilot.currentCase`;
- Supabase Auth session не хранится в `lifepilot.caseHistory`;
- password, access token, refresh token, admin email, role и allowlist data не сохраняются в `localStorage` LifePilot MVP;
- проверка session и `public.admin_users` allowlist выполняется server-side перед показом `/admin`;
- logout закрывает admin session, но не очищает локальную историю кейсов;
- основной пользовательский MVP продолжает работать через `localStorage` без auth.

План этапа Auth/Admin и Vercel не является source of truth для state management. Состояние Auth/Admin определяется ADR и specs.

## Передача данных между экранами

Данные не передаются через query params и не должны попадать в URL. Это важно, потому что исходный текст может содержать чувствительную информацию.

Основной механизм передачи:

1. экран `Новый кейс` создает объект кейса после локального анализа текста;
2. объект записывается в `lifepilot.currentCase`;
3. этот же объект добавляется в `lifepilot.caseHistory`;
4. экран `Анализ` проверяет наличие текущего кейса;
5. экран `Результат` читает текущий кейс из `localStorage`;
6. экран `История` читает список кейсов;
7. при действии `Открыть результат` из истории выбранная запись снова записывается в `lifepilot.currentCase`;
8. пользователь переходит к экрану результата.

Просмотр detail route `/history/[caseId]` читает запись из `lifepilot.caseHistory` и не обязан изменять `lifepilot.currentCase`.

Маршрут показывает, какой экран открыт, но не содержит содержимое кейса.

## Производные данные

Часть данных можно вычислять повторно из сохраненного кейса:

- `riskLevel`, если он отсутствует в старой записи;
- короткий preview текста;
- заголовок карточки истории;
- человекочитаемая дата;
- текстовые рекомендации по уровню риска.

Такие данные не нужно считать самостоятельным источником правды. Источником правды остается сохраненный кейс.

## Правила состояния

- Пустой текст не создает кейс.
- Кейс не должен переходить к результату без исходного текста.
- Если `lifepilot.currentCase` отсутствует, экран анализа возвращает пользователя к созданию кейса.
- Если результат не может прочитать текущий кейс, он показывает безопасное пустое состояние и предлагает начать заново.
- Если старая запись истории не содержит категорию, используется резервное значение `Другое`.
- Если старая запись истории не содержит `riskLevel`, он рассчитывается заново из текста.
- Открытие кейса из истории не создает новый кейс, а восстанавливает выбранный кейс как текущий.
