# Routing map MVP LifePilot

## Назначение документа

Этот документ описывает маршруты frontend MVP, переходы, fallback-поведение, error routes, empty states, deep-link риски и мобильную навигацию. Он не задает конкретную технологию роутинга и не требует реализации маршрутов прямо сейчас.

## Принципы роутинга MVP

Роутинг должен поддерживать линейный сценарий:

1. Пользователь понимает ограничения.
2. Создает кейс.
3. Запускает анализ.
4. Смотрит результат.
5. Проверяет немецкий черновик.
6. Сохраняет кейс.
7. Возвращается к истории.

Маршруты должны быть короткими и предсказуемыми. В MVP не нужно создавать вложенную навигационную систему для будущих функций.

## Список routes

Условная карта маршрутов:

- `/onboarding` — первый запуск и границы ответственности.
- `/` — главный экран.
- `/case/new` — создание кейса.
- `/case/analyzing` — анализ документа.
- `/case/result` — результат текущего кейса.
- `/case/draft` — немецкий черновик текущего кейса.
- `/case/high-risk` — статический экран предупреждения о риске в текущем MVP.
- `/history` — история кейсов.
- `/history/:caseId` — просмотр сохраненного кейса.
- `/settings/safety` — настройки безопасности.
- `/error` — общий экран ошибки.
- fallback route — неизвестный маршрут.

`:caseId` является параметром route `app/history/[caseId]/page.tsx`. Экран читает локальную историю из `localStorage`, ищет сохраненный кейс по `id` и показывает detail view без backend, auth или Supabase-запроса.

## Protected и unprotected routes

В MVP нет аккаунтов, ролей и auth-защиты.

Unprotected routes:

- `/onboarding`;
- `/`;
- `/case/new`;
- `/history`;
- `/settings/safety`;
- `/error`;
- fallback route.

State-guarded routes:

- `/case/analyzing` — нужен текущий черновик кейса с исходным текстом;
- `/case/result` — нужен результат анализа или сохраненный кейс;
- `/case/draft` — нужен текущий кейс для показа демонстрационного черновика;
- `/history/:caseId` — нужен существующий сохраненный кейс.

State-guarded не означает защищенный auth-маршрут. Это значит, что экран не должен открываться без нужного состояния кейса.

## Переходы

### Первый запуск

- `/onboarding` -> `/`;
- `/onboarding` -> `/settings/safety`, если пользователь открывает правила безопасности;
- `/settings/safety` -> `/`.

### Основной сценарий

- `/` -> `/case/new`;
- `/case/new` -> `/case/analyzing`;
- `/case/analyzing` -> `/case/result`;
- `/case/result` -> `/case/draft`;
- `/case/high-risk` доступен как отдельный информационный экран через навигацию;
- `/case/draft` -> `/case/result`;
- `/case/result` -> `/history`, если кейс сохранен и пользователь переходит в историю.

### История

- `/` -> `/history`;
- `/history` -> `/history/:caseId`;
- `/history/:caseId` -> `/case/result` или отдельный режим просмотра результата;
- `/history` -> `/case/new`.

### Ошибки

- любой экран -> `/error`, если невозможно продолжить безопасно;
- `/error` -> предыдущий безопасный экран;
- `/error` -> `/case/new`, если ошибка связана с вводом;
- `/error` -> `/`, если состояние восстановить нельзя.

## Fallback behavior

Если пользователь открывает неизвестный маршрут:

- показать понятный fallback;
- предложить перейти на главный экран;
- не создавать новый кейс автоматически;
- не запускать анализ автоматически.

Если пользователь открывает state-guarded route без нужного состояния:

- `/case/analyzing` без текста -> `/case/new`;
- `/case/result` без результата -> `/case/new` или `/history`, если есть сохраненные кейсы;
- `/case/draft` без результата -> `/case/result`, если результат есть, иначе `/case/new`;
- `/history/:caseId` с неизвестным id -> `/history` с empty или error state.

Fallback не должен скрывать потерю данных. Если текущий ввод потерян, пользователь должен увидеть понятное сообщение.

## Error routes

`/error` используется для ошибок, которые нельзя безопасно показать inline.

Типы ошибок:

- не удалось выполнить анализ;
- не удалось сформировать немецкий черновик;
- не удалось прочитать сохраненный кейс;
- не удалось сохранить кейс;
- состояние маршрута повреждено;
- пользователь открыл экран без нужных данных.

Ошибки ввода лучше показывать inline на экране создания кейса:

- пустой текст;
- смешанные языки;
- непонятный документ.

## Empty states

Empty states должны быть частью маршрутов, а не отдельными продуктами.

Минимальные empty states:

- история пуста;
- нет последнего кейса на главном экране;
- нет результата анализа;
- немецкий черновик недоступен;
- будущий template-only режим недоступен;
- сохраненный кейс не найден.

Каждый empty state должен иметь безопасное следующее действие:

- создать кейс;
- вернуться на главный экран;
- изменить исходный текст;
- открыть результат анализа;
- прочитать настройки безопасности.

## Deep-link risks

Deep-link в MVP рискован, потому что часть экранов зависит от текущего состояния кейса.

Риски:

- пользователь открывает `/case/draft` без анализа;
- пользователь открывает старый сохраненный кейс, где warnings могли устареть;
- URL раскрывает идентификатор или чувствительный смысл кейса;
- пользователь попадает сразу к черновику и пропускает предупреждения.

Правила:

- deep-link на черновик должен сначала проверить наличие текущего кейса;
- автоматическая high-risk блокировка черновика и замена его общим шаблоном пока не реализованы и должны быть отдельной safety-задачей;
- сохраненный кейс должен открываться с результата анализа или detail view, а не с экрана черновика;
- route state не должен содержать полный исходный текст документа;
- чувствительные данные не должны попадать в URL.

## Mobile navigation logic

Мобильная навигация строится вокруг одного основного действия на экране.

Правила:

- header содержит назад и короткий контекст;
- bottom actions содержит главный следующий шаг;
- назад возвращает к предыдущему смысловому шагу, а не всегда на главный экран;
- системный back не должен терять введенный текст без предупреждения;
- при high-risk состоянии текущий путь должен показать предупреждение; будущая блокировка черновика должна вести к безопасному варианту;
- история и настройки доступны как вспомогательные маршруты;
- onboarding не должен появляться повторно, если пользователь уже прошел его, кроме ручного открытия правил безопасности.

## Protected behavior без auth

Так как auth в MVP отсутствует, защита маршрутов должна быть продуктовой:

- нельзя открыть анализ без текста;
- нельзя открыть результат без анализа или сохраненного кейса;
- нельзя открыть черновик без результата;
- текущий MVP не блокирует черновик автоматически; будущая high-risk блокировка не должна позволять открыть конкретный немецкий ответ без безопасного промежуточного шага;
- нельзя открыть сохраненный кейс, если кейс не существует.

Это поведение должно быть описано как routing guard, но не как система прав доступа.

## Где возможна навигационная сложность

Особенно внимательно нужно отнестись к переходам:

- `результат анализа` -> `немецкий черновик`;
- `результат анализа` -> `немецкий черновик` при high-risk кейсе;
- будущая связка `результат анализа` -> `high-risk warning` -> `template-only режим`;
- `история` -> `сохраненный кейс`;
- `ошибка` -> `восстановление предыдущего состояния`;
- `создание кейса` -> `назад` при несохраненном тексте.

Эти переходы влияют на безопасность MVP и не должны решаться только визуально.
