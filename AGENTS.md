# Инструкции для агентов LifePilot

## Назначение

`AGENTS.md` — главный рабочий регламент для ИИ-агентов в проекте LifePilot. Документ не заменяет specs, plans, architecture, design или testing, а помогает понять, какие документы проверять и в каком порядке принимать решения.

## Язык проекта

Документация, комментарии и пользовательские тексты пишутся на русском языке. Немецкий язык допустим для примеров писем и черновиков ответов. Имена файлов, маршрутов, переменных, API и технических сущностей сохраняются в принятом техническом формате.

## Startup Workflow

Перед любой задачей:

1. Проверить `git status`.
2. Прочитать `AGENTS.md`.
3. Проверить `docs/project-map.md`.
4. Найти релевантные specs в `docs/specs/`.
5. Проверить активные планы в `docs/plans/active/`.
6. Проверить связанные документы в `docs/architecture/`, `docs/design/` и `docs/testing/`.
7. Только после этого выполнять изменения.

## Delivery Workflow

Для задач, которые меняют код, поведение, структуру или документацию проекта, использовать порядок:

1. Plan: найти существующий active plan или создать новый в `docs/plans/active/`, если задачи еще нет.
2. Approve: не начинать реализацию нового scope без явного подтверждения пользователя или уже утвержденного active plan.
3. Implementation: менять только файлы, нужные для утвержденного scope.
4. Testing: выполнить релевантные проверки и `npm run build`, если изменение затрагивает код или конфигурацию.
5. Docs update: обновить specs, plans, architecture, design или testing только если они реально изменились.
6. Changelog: обновить `docs/changelog.md` при значимом изменении.
7. Project Map: обновить `docs/project-map.md` при создании, удалении, переносе файлов или изменении структуры.
8. Commit: перед commit проверить `git status`, diff и отсутствие лишних файлов.

## Source Of Truth

При конфликте документов использовать следующий приоритет:

1. MVP Scope: `docs/plans/active/mvp-scope.md`.
2. Specs: `docs/specs/`.
3. Architecture: `docs/architecture/`.
4. Design: `docs/design/`.
5. Active Plans: `docs/plans/active/`.
6. Code.

Код не является источником требований. Если код расходится с требованиями, сначала уточнить и обновить документацию, затем менять реализацию.

Текущая утвержденная задача определяет рамки работы агента, но не заменяет источники требований проекта. Если запрос расширяет MVP scope, сначала нужен approved plan и обновление релевантных specs.

`docs/roadmap.md`, `docs/mvp-status.md`, `docs/changelog.md` и `docs/project-map.md` не являются источниками требований. Они показывают статус, навигацию и историю изменений. Если они противоречат MVP Scope, specs или architecture, сначала исправить источник требований или уточнить решение, затем синхронизировать эти документы.

## Rules For Specs

Перед изменением новой функции, поведения системы, модели данных, auth, безопасности, маршрутов или MVP scope сначала обновлять релевантные specs, затем код.

Если specs не покрывают задачу, нельзя додумывать требования только по коду. Нужно зафиксировать требование в `docs/specs/` или обновить существующий spec.

## Rules For Plans

- Новые планы создавать только в `docs/plans/active/`.
- `docs/plans/active/` содержит только незавершенные задачи.
- `docs/plans/completed/` является архивом завершенных работ.
- После завершения переносить план из `active` в `completed`.
- Перед переносом проверять содержание, ссылки и соответствие текущему состоянию проекта.
- После переноса обновлять `docs/project-map.md` при необходимости.

## Project Map

`docs/project-map.md` является картой проекта и точкой входа в документацию.

Обновлять `docs/project-map.md` при:

- создании файлов;
- удалении файлов;
- переносе файлов;
- существенном изменении структуры проекта или документации.

## Changelog

`docs/changelog.md` фиксирует значимые изменения проекта.

Обновлять changelog при изменении пользовательского поведения, архитектуры, specs, plans, security/Auth/Supabase правил, Git workflow, структуры документации или release/deploy статуса. Changelog обновляет тот, кто вносит соответствующее изменение.

## Git Workflow

Перед началом работы:

- проверить `git status`.

Перед commit:

- проверить измененные файлы;
- убедиться, что изменения относятся только к текущей задаче;
- не добавлять случайные, временные или сгенерированные файлы.

Перед push:

- убедиться, что build проходит;
- убедиться, что документация синхронизирована с кодом;
- убедиться, что планы актуальны;
- проверить структуру проекта и `docs/project-map.md`.

## Security Rules

Запрещено коммитить:

- `.env`;
- `.env.local`;
- реальные ключи и токены;
- `service_role` keys;
- `.next/`;
- `node_modules/`;
- `.vercel/`;
- файлы с персональными данными пользователей.

## Auth / Supabase Rules

Любые изменения auth, RLS, admin access, database schema, `public.cases` или `public.admin_users` должны сначала проверяться через specs и архитектурную документацию.

Нельзя менять доступ к данным, RLS policies, admin-права или Supabase schema только на основании кода без проверки документации.

## Разделы документации

- Specs: `docs/specs/`
- Plans: `docs/plans/`
  - Active plans: `docs/plans/active/`
  - Completed plans: `docs/plans/completed/`
- Design: `docs/design/`
- Architecture: `docs/architecture/`
- Testing: `docs/testing/`
- Project Map: `docs/project-map.md`
- Changelog: `docs/changelog.md`

## Definition Of Done

Implementation-задача считается завершенной только если:

- код реализован в рамках утвержденного scope;
- документация актуальна;
- specs актуальны;
- планы обновлены;
- changelog обновлен при необходимости;
- build проходит, если изменение затрагивает код или конфигурацию;
- проверки выполнены;
- `docs/project-map.md` обновлен при необходимости.

Docs-only задача считается завершенной только если:

- нужные документы обновлены;
- требования, roadmap/status и project-map не противоречат друг другу;
- changelog обновлен при необходимости;
- код приложения не изменен.

Audit-only задача считается завершенной только если:

- аудит выполнен по запрошенному scope;
- проблемы разделены по критичности;
- файлы не изменены.

## Общие правила

- Не создавать случайные или лишние файлы.
- Сначала искать существующий документ или модуль, затем создавать новый файл только при явной необходимости.
- Не дублировать содержимое specs, plans, architecture, design или testing в `AGENTS.md`.
- Перед push сначала проверить plans, документацию и структуру проекта.
